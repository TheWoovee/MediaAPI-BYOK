# Local access: how the browser at https://www.thewoovee.com/studio reaches servers on the user's PC

- Applies to: `comfyui.md`, `a1111-forge.md`, `swarmui-invoke.md` (all `direct` transport)
- Last verified: 2026-09-06. Sources were read from the doc sites' source repositories where the sites themselves were blocked in the research sandbox: MDN → github.com/mdn/content (`files/en-us/web/security/defenses/mixed_content/index.md`) and github.com/mdn/browser-compat-data (`http/mixed-content.json`, `api/Permissions.json`); W3C Secure Contexts → github.com/w3c/webappsec-secure-contexts `index.bs`; Local Network Access → github.com/WICG/local-network-access (`explainer.md`, `index.bs`); Cloudflare → github.com/cloudflare/cloudflare-docs (`src/content/docs/...` and `src/content/partials/...` paths cited inline; canonical URLs given where known); Tailscale → github.com/tailscale/tailscale CLI/`ipn` source plus tailscale.com/kb/1223 search snippets (KB page itself unreachable → those items marked accordingly).
- Two connection modes the app must support:
  1. **Same PC**: page on `https://www.thewoovee.com` → `http://127.0.0.1:8188` / `:7860`.
  2. **Anywhere**: page → `https://comfy.thewoovee.com` / `https://sd.thewoovee.com` (Cloudflare Tunnel on the user's PC, optionally behind Cloudflare Access), or a Tailscale Funnel URL.

## a. Browser rules: mixed content and Local Network Access

### Mixed content (https page → http://localhost)
- Spec: a request is mixed content only if its URL is **not "potentially trustworthy"**. Secure Contexts §3.1 (w3c `index.bs`, verified): an origin whose host matches `127.0.0.0/8` or `::1/128` is *Potentially Trustworthy*; `localhost`, `localhost.`, `*.localhost` are too **if** the UA guarantees they resolve to loopback ("let-localhost-be-localhost"). Therefore `http://127.0.0.1:8188` and `http://localhost:8188` are **not mixed content by spec**; `http://192.168.x.x` / `http://10.x` / `http://<lan-hostname>` **are** (blockable mixed content — `fetch`/XHR/WebSocket are "blockable", never auto-upgraded to https in a way that would help, so they are simply blocked).
- MDN (Defenses/Mixed_content, verified): "Local resources are considered to be from secure origins, just like HTTPS origins. This includes `file:` URLs, and content accessed from loopback addresses such as `http://127.0.0.1/` or `http://localhost/`."
- Browser support (MDN browser-compat-data `http/mixed-content.json`, verified 2026-09-06):
  | Sub-feature | Chrome | Edge | Firefox | Safari |
  |---|---|---|---|---|
  | `allow_loopback_url` (`http://127.0.0.1`, `[::1]`) | ≤79 (i.e. long-standing; Chromium bug 41338472 snippet says exempt since Chrome 53) | mirrors Chrome | **55** | **false (blocked)** |
  | `allow_localhost_url` (`http://localhost`, `*.localhost` by name) | ≤79 | mirrors Chrome | **84** (Firefox 84 release notes: "Firefox 84 and later allow loading of mixed content on http://localhost/ and http://*.localhost/ URLs") | **false (blocked)** |
  - **Chrome / Edge**: allowed for both `127.0.0.1` and `localhost` (any current version).
  - **Firefox**: allowed for `127.0.0.1` since 55 and `localhost` since 84.
  - **Safari (WebKit)**: **still blocks** http://localhost and http://127.0.0.1 from an https page as of 2026 (BCD `false`; WebKit bug 171934 "Don't treat loopback addresses as mixed content" remains open per search results; developer reports: "Safari is the only browser that blocks mixed-content http://localhost requests"). The app must tell Safari users to use Chrome/Firefox/Edge for the same-PC mode, or to use the tunnel (https) mode.
  - `http://192.168.x.x`, `http://10.x.x.x`, `http://mypc.local`: **blocked as mixed content in every browser** from an https page. Exception (Chrome only, 142+): a `fetch()` annotated with `targetAddressSpace: "local"` to a *private-IP literal or `.local` name* is exempted from mixed-content blocking **but** then gated by the Local Network Access permission (below). Firefox/Safari: no exemption. Recommendation: do not offer LAN-IP mode in v1; offer localhost + tunnel only.
- Practical: use `http://127.0.0.1:<port>` rather than `http://localhost:<port>` as the default (works in Firefox ≥55 too, avoids IPv6/`localhost` resolution quirks; ComfyUI's default-middleware Host/Origin check treats both as loopback).

### Chrome "Local Network Access" (LNA) — the 2025/2026 rules
- Replaces the abandoned "Private Network Access" preflight design (`Access-Control-Request-Private-Network: true` / `Access-Control-Allow-Private-Network: true` headers). BCD: the PNA preflight was in Chrome 124–137 (warning-only/opt-in) and was **removed in 138**, where it only survives behind the `#local-network-access-check` flag; **no server-side header is needed or honoured any more** (WICG LNA explainer: "differs by gating access on a permission rather than via preflight requests"; "this approach should only require changes to sites that need to access the local network").
- Address spaces: `loopback` (127/8, ::1, `localhost`), `local` (RFC1918/4193 private IPs, `.local` names), `public`. A **local network request** is `public → local`, `public → loopback`, or `local → loopback` (explainer §"Local network requests"; the developer.chrome.com blog snippet: "A local network request is any request from a public website to a local IP address or loopback").
- **Our case `https://www.thewoovee.com` (public) → `http://127.0.0.1:8188` (loopback) IS a local network request** and, from **Chrome 142** (permission prompt launch, per developer.chrome.com/blog/local-network-access; BCD: Permissions API name `local-network-access` version_added 142, split into `local-network` and `loopback-network` in Chrome 145 with `local-network-access` kept as alias), Chrome:
  1. requires the page to be a secure context (we are https — OK);
  2. shows a **one-time permission prompt** ("allow www.thewoovee.com to look for and connect to devices on your local network"); if denied, the fetch fails with a network error (`TypeError: Failed to fetch`);
  3. remembers the grant per origin (site settings → "Local network access").
  - The **server needs to do nothing** (no preflight header). CORS still applies normally on top.
  - `fetch(url, { targetAddressSpace: "loopback" })` (or `"local"`) tells Chrome up front that the target is loopback/local: it (a) makes the request bypass mixed-content checks for http URLs and (b) triggers the prompt deterministically; if the resolved IP is not in that space the request fails (explainer §"Integration with Fetch"). For `127.0.0.1`/`localhost` targets Chrome already knows a priori, so the option is optional, but adding `targetAddressSpace: 'loopback'` is harmless and future-proof. Other browsers ignore unknown `RequestInit` keys.
  - WebSockets go through the same gate (explainer §"Websockets").
  - Permissions Policy: `local-network-access` (alias) / `local-network`, `loopback-network`, default allowlist `'self'` — only matters if the studio ran in an iframe (it does not).
  - Enterprise policies `LocalNetworkAccessRestrictionsEnabled` / `LocalNetworkAccessAllowedForUrls` exist (chromeenterprise.google policy list — page unreachable in the sandbox; names from search results, **unverified**).
  - Firefox and Safari have **not** shipped LNA (BCD `false`).
- Design consequence: the "Test connection" button must be a user gesture and the UI must explain the Chrome prompt; detect a rejected prompt via `navigator.permissions.query({name: 'local-network-access'})` (Chrome ≥142; wrap in try/catch since the name throws elsewhere) and show a "click the 🔒 icon → Local network access → Allow" hint.

## b. Cloudflare Tunnel — step by step
Cloudflare Tunnel is available on all plans including Free (`tunnel/index.mdx`: `<Plan type="all" />`). `cloudflared` makes outbound-only connections; no port-forwarding. Two management styles:

### b.1 Locally-managed tunnel (CLI + `config.yml`) — Windows and Linux
Source: cloudflare-docs `docs/tunnel/advanced/local-management/create-local-tunnel.mdx`, `configuration-file.mdx`, `partials/cloudflare-one/tunnel/locally-managed/as-a-service/windows.mdx`, `.../linux.mdx`, `partials/cloudflare-one/tunnel/downloads.mdx` (canonical: https://developers.cloudflare.com/tunnel/advanced/local-management/…).
1. **Install `cloudflared`**
   - Windows: download `cloudflared-windows-amd64.exe` or `.msi` from https://github.com/cloudflare/cloudflared/releases/latest (docs downloads page); rename to `cloudflared.exe`; the docs recommend `C:\Cloudflared\bin\cloudflared.exe`. (Community note: `winget install --id Cloudflare.cloudflared` also works — not in the official page, **unverified**.) "Instances of `cloudflared` do not automatically update on Windows."
   - Debian/Ubuntu (partial `cloudflared-debian-install.mdx`):
     ```sh
     sudo mkdir -p --mode=0755 /usr/share/keyrings
     curl -fsSL https://pkg.cloudflare.com/cloudflare-main.gpg | sudo tee /usr/share/keyrings/cloudflare-main.gpg >/dev/null
     echo "deb [signed-by=/usr/share/keyrings/cloudflare-main.gpg] https://pkg.cloudflare.com/cloudflared any main" | sudo tee /etc/apt/sources.list.d/cloudflared.list
     sudo apt-get update && sudo apt-get install cloudflared
     ```
     RHEL: `curl -fsSl https://pkg.cloudflare.com/cloudflared.repo | sudo tee /etc/yum.repos.d/cloudflared.repo && sudo yum install cloudflared`; Arch: `pacman -Syu cloudflared`; macOS: `brew install cloudflared`.
2. **Login** (needs a domain already on Cloudflare with Cloudflare nameservers — prerequisite in the doc; so `thewoovee.com` must be the *user's* zone, or you must give each user their own subdomain zone — see Gotchas):
   `cloudflared tunnel login` → browser opens, pick the zone → writes `cert.pem` to the default directory (`%USERPROFILE%\.cloudflared` on Windows; `~/.cloudflared`, `/etc/cloudflared`, `/usr/local/etc/cloudflared` on Unix — `local-tunnel-terms.mdx`).
3. **Create the tunnel**: `cloudflared tunnel create woovee-studio` → prints the tunnel **UUID** and writes `<UUID>.json` (credentials) into the default dir; check with `cloudflared tunnel list`.
4. **`config.yml`** in the default dir (`%USERPROFILE%\.cloudflared\config.yml` / `~/.cloudflared/config.yml`) with **two ingress rules and the mandatory catch-all** (`configuration-file.mdx`: "Configuration files that contain ingress rules must always include a catch-all rule that concludes the file"):
   ```yml
   tunnel: <Tunnel-UUID>
   credentials-file: C:\Users\<you>\.cloudflared\<Tunnel-UUID>.json   # Linux: /home/<you>/.cloudflared/<Tunnel-UUID>.json
   # logfile: C:\Cloudflared\cloudflared.log
   ingress:
     - hostname: comfy.thewoovee.com
       service: http://localhost:8188
     - hostname: sd.thewoovee.com
       service: http://localhost:7860
     - service: http_status:404
   ```
   Validate: `cloudflared tunnel ingress validate`; test matching: `cloudflared tunnel ingress rule https://comfy.thewoovee.com`. Per-service origin options go under `originRequest:` (e.g. `connectTimeout: 30s` default, `noTLSVerify`, `httpHostHeader`, `keepAliveTimeout: 1m30s`, `tcpKeepAlive: 30s`, `http2Origin`) — `partials/cloudflare-one/tunnel/origin-parameters.mdx`. cloudflared forwards the full path unchanged.
5. **DNS**: `cloudflared tunnel route dns <UUID or NAME> comfy.thewoovee.com` and again for `sd.thewoovee.com` — each creates a proxied CNAME → `<UUID>.cfargotunnel.com` (requires `cert.pem`). "You can also create multiple DNS records pointing to the same tunnel subdomain" (`dns-records-create.mdx`). Alternatively add the CNAMEs in the dashboard (DNS → Records → CNAME, target `<UUID>.cfargotunnel.com`, proxied).
6. **Run**: `cloudflared tunnel run woovee-studio` (or `cloudflared tunnel --config <path> run <NAME>`); check `cloudflared tunnel info woovee-studio`.
7. **Run as a Windows service** (`as-a-service/windows.mdx`, verified): as admin in `C:\Cloudflared\bin`: `cloudflared.exe service install`; `mkdir C:\Windows\System32\config\systemprofile\.cloudflared`; copy `cert.pem`, `<Tunnel-ID>.json` and `config.yml` from `C:\Users\%USERNAME%\.cloudflared\` into that folder (the service runs as LocalSystem, whose profile is `systemprofile`); in `regedit` set `HKLM\SYSTEM\CurrentControlSet\Services\Cloudflared\ImagePath` to `C:\Cloudflared\bin\cloudflared.exe --config=C:\Windows\System32\config\systemprofile\.cloudflared\config.yml tunnel run`; then `sc start cloudflared` (`sc stop cloudflared` / `sc start cloudflared` after config changes). Logs: `logfile:` key in config.yml.
8. **Run as a Linux service** (`as-a-service/linux.mdx`): `sudo cloudflared --config /home/<USER>/.cloudflared/config.yml service install` (the doc notes `$HOME` is `/root` under sudo, so pass `--config`), `systemctl start cloudflared`, `systemctl status cloudflared`, `systemctl restart cloudflared`.

### b.2 Remotely-managed (dashboard) tunnel — the easier path for end users
Source: `docs/cloudflare-one/networks/connectors/cloudflare-tunnel/get-started/create-remote-tunnel.mdx` + partials `tunnel/create-tunnel.mdx`, `tunnel/add-published-application.mdx` (canonical https://developers.cloudflare.com/cloudflare-one/networks/connectors/cloudflare-tunnel/get-started/create-remote-tunnel/).
1. Zero Trust dashboard → **Networking → Tunnels → Create a tunnel** (connector: Cloudflared) → name it → **Create Tunnel**.
2. Pick the OS; copy the shown command, e.g. Windows: `cloudflared.exe service install <TOKEN>` (or `msiexec` line + service install), Linux: `sudo cloudflared service install <TOKEN>`. Manual run: `cloudflared tunnel --loglevel info run --token <TOKEN>` (`tunnel/configuration.mdx`). Wait for "connected" → Continue.
3. **Routes tab → Add route → Published application**: subdomain `comfy`, domain `thewoovee.com`, Service URL `http://localhost:8188`; repeat with `sd` → `http://localhost:7860`. Cloudflare creates the proxied CNAME automatically. Multiple published applications per tunnel are supported (`tunnel/routing.mdx`: "You can publish multiple applications on a single tunnel"). Multi-level subdomains (`a.b.thewoovee.com`) need an Advanced Certificate — stick to one level.
4. Per-route "Additional application settings" expose the same origin parameters (`HTTP Host Header`, `Disable TLS verification`, `Connect Timeout` 30s, `TCP Keep Alive` 30s, `Idle Connection Expiration Time` 1m30s, `Use HTTP/2 to origin`, and **Access → Protect with Access** = cloudflared validates the Access JWT itself: `access: {required: true, teamName, audTag: [...]}` in config terms).
5. No `config.yml`, no `cert.pem`, no registry editing — configuration lives in the dashboard, token in the service. Recommended for the end-user checklist.

- **Effect on ComfyUI**: `POST /prompt` returns in milliseconds and `GET /history/{id}` is instant, so a 30-minute video render never trips the 125 s limit **as long as the app polls** rather than holding a request open. Only `/view` downloads > 100 s of transfer or `/upload/*` > 100 MB are at risk. WS `/ws` is fine but treat as optional.
- **Effect on A1111/Forge**: `txt2img`/`img2img` are synchronous → any generation longer than ~125 s returns **524** (the job still completes on the PC). Use `save_images: true` remotely and keep steps/sizes modest, or prefer ComfyUI for remote heavy jobs (`a1111-forge.md`).
- Connection-timeout note from `error-524.mdx`: "Implement status polling of large HTTP processes to avoid hitting this error" — i.e. exactly the ComfyUI history-polling design.
- Zone requirement: hostnames must be in a zone in the **same Cloudflare account** as the tunnel; `thewoovee.com` belongs to the app owner, so end users cannot get `comfy.thewoovee.com` on their own account. Either (a) users bring their own domain (`comfy.<userdomain>`), or (b) the app owner runs the Zero Trust account and provisions per-user tunnels/hostnames centrally (heavier ops), or (c) users use Tailscale Funnel / quick tunnels (`cloudflared tunnel --url http://localhost:8188` gives a random `*.trycloudflare.com` https URL, no account; no Access, URL changes each run, no WebSocket/upload guarantees — note "Quick tunnels do not need a configuration file", `configuration-file.mdx`). The app should accept *any* https base URL.

## c. Cloudflare Access in front of the tunnel hostname
Sources: `docs/cloudflare-one/access-controls/applications/http-apps/self-hosted-public-app.mdx`, partial `access/self-hosted-app/generic-public-app.mdx`, `integrations/identity-providers/one-time-pin.mdx`, `access-controls/policies/index.mdx`, `access-controls/service-credentials/service-tokens.mdx`, `applications/http-apps/authorization-cookie/index.mdx`, `.../cors.mdx`, `.../application-token.mdx`, `access-settings/session-management.mdx`, Terraform `cloudflare_zero_trust_access_application` docs (field names). Canonical CORS page: https://developers.cloudflare.com/cloudflare-one/access-controls/applications/http-apps/authorization-cookie/cors/

### c.1 Create the application and an email (OTP) Allow policy
1. Zero Trust → **Integrations → Identity providers → Add new identity provider → One-time PIN** (new orgs default to the "Cloudflare" IdP; OTP must be added explicitly — `one-time-pin.mdx`).
2. Zero Trust → **Access controls → Applications → Create new application → Self-hosted and private → Add public hostname**: Domain `thewoovee.com`, subdomain `comfy` (add a second public hostname `sd` in the same app so one login covers both — "Multi-domain applications": Access issues the cookie for each domain in the app; with **Eager redirect cookie** (default on for new apps) it pre-sets the cookie on every concrete domain via redirects right after login).
3. **Access policies**: add a policy Action **Allow**, rule type **Include**, selector **Emails** = the user's address(es) (or **Emails ending in**). "All Access applications are deny by default." One-time PIN: user enters the email, gets a 6-digit code valid 10 min, single-use.
4. Identity providers: tick One-time PIN; optionally "Apply instant authentication".
5. **Session Duration** (application token lifetime): default 24 h; range immediate → 1 month (`session-management.mdx`). Global session (IdP re-login) default 24 h, 15 min → 1 month.
6. Advanced settings → **Cross-Origin Resource Sharing (CORS) settings** and **Cookie settings** (below) → Create.
7. Connect the origin: the tunnel route (b.2 step 3); optionally enable **Protect with Access** on the route so cloudflared rejects anything that bypasses Access.

### c.2 How Access + CORS + preflight actually behave (critical for the app)
- Every request to `comfy.thewoovee.com` must carry a valid `CF_Authorization` cookie (application token JWT set on that hostname) **or** service-token headers; otherwise Access returns a **302 to the login page** (HTML) — for `fetch` this surfaces as an opaque redirect/CORS failure, never as JSON.
- **Preflight problem** (`cors.mdx`, verified): "If you make a preflighted cross-origin request to an Access-protected domain, the OPTIONS request will return a `403` error. This error occurs regardless of whether you have logged in to the domain. This is because the browser never includes cookies with OPTIONS requests, by design." Three fixes:
  1. **Bypass OPTIONS requests to origin** (Advanced settings → CORS settings → toggle "Bypass options requests to origin"; API/Terraform field `options_preflight_bypass: true`, "Cannot turn on if cors_headers is set"): OPTIONS goes straight to ComfyUI/A1111, which answer it themselves (ComfyUI needs `--enable-cors-header https://www.thewoovee.com`; A1111 `--cors-allow-origins=...`). "This will remove all existing CORS settings for this application."
  2. **Configure Cloudflare to respond to the OPTIONS request**: fill in the app's CORS settings (`cors_headers`: `allowed_origins` [list] or `allow_all_origins`, `allowed_methods` or `allow_all_methods`, `allowed_headers` or `allow_all_headers`, `allow_credentials`, `max_age`) → Cloudflare answers the preflight itself and "the OPTIONS request never reaches your origin". Then "the browser will then send the main request which does include the authentication cookie (assuming you have logged into the Access-protected domain)". **The actual GET/POST response still needs CORS headers from the origin** (Access does not add them to non-OPTIONS responses — the doc says to configure Access "to match the response headers sent by your origin"), so the origin server flags remain required in both options.
  3. A Cloudflare Worker on `www.thewoovee.com/api/*` that injects `cf-access-client-id` / `cf-access-client-secret` (service token) and forwards to `comfy.thewoovee.com` — same-origin for the browser, no CORS at all, no login. Docs' own recipe (`cors.mdx` §"Send authentication token with Cloudflare Worker"); the Worker strips `set-cookie`. Costs: all media flows through the Worker (Worker request/CPU limits; 100 MB body still applies) and the app owner would hold each user's service token unless the Worker reads it from a per-user header/KV.
- **Recommended Access CORS settings for option 2** (matching ComfyUI's own headers): allowed origins `https://www.thewoovee.com`; methods `GET, POST, OPTIONS` (+ `DELETE, PUT, PATCH` harmless); allowed headers `Content-Type, Authorization` (add `CF-Access-Client-Id, CF-Access-Client-Secret` only if using service tokens from the browser); **Allow credentials = on** (needed so the browser sends `CF_Authorization`); Max age e.g. 600. Note: `allow_all_origins` (`*`) with `allow_credentials` is invalid for credentialed requests — always list the exact origin.
- **Bypass policy for OPTIONS**: Access policy action **Bypass** exists (policies index: "disables Access enforcement for specific traffic … Bypass policies do not support identity-based rule types"), but a policy cannot match on HTTP method, so it cannot single out OPTIONS. The per-app **"Bypass options requests to origin"** toggle is the intended mechanism; do not use a Bypass policy (it would open the whole hostname).
- **Cookie reuse from `www.thewoovee.com` with `credentials: 'include'`**:
  - `CF_Authorization` (application token) is a cookie on `comfy.thewoovee.com` (host of the Access app), `HttpOnly` admin choice (default on), `SameSite` admin choice, **default `None`** ("Cookies will be sent in all contexts, including cross-origin requests") — `authorization-cookie/index.mdx` table "CF_Authorization (Access application domain)": HttpOnly "Admin choice (Default: None)", SameSite "Admin choice (Default: None)". Keep SameSite = None (the doc warns Strict causes redirect loops; Lax would drop the cookie on cross-site POST/XHR).
  - A fetch from origin `https://www.thewoovee.com` to `https://comfy.thewoovee.com` is **cross-origin but same-site** (same registrable domain `thewoovee.com`), so browsers treat the cookie as first-party — Chrome's third-party-cookie restrictions and Safari ITP do **not** block it. With `credentials: 'include'` the browser attaches `CF_Authorization`. (`cors.mdx` recommends `credentials: 'same-origin'` for the docs' same-domain scenario; for our cross-origin case `include` is required.) Do not test in Incognito ("Do not troubleshoot CORS in Incognito mode … `CF-Authorization` being blocked as a third-party cookie").
  - The cookie is scoped to the *app hostname*, not the zone; the app cannot read it (HttpOnly) and does not need to. **Login flow for the app**: open `https://comfy.thewoovee.com/system_stats` in a new tab/popup → user completes OTP → Access sets the cookie → user closes the tab → app retries the fetch with `credentials: 'include'`. Detect "not logged in" as a fetch that fails/redirects (`response.type === 'opaqueredirect'` with `redirect: 'manual'`, or a CORS TypeError) and show the "Log in to your tunnel" button.
  - Because the cookie is per-hostname, `sd.thewoovee.com` needs its own cookie; putting both hostnames in **one** Access application with Eager redirect cookie on means one OTP login sets both.
  - Session length = Session Duration (default 24 h); after expiry the fetch fails again → re-run the login popup. Global session token lives on `<team>.cloudflareaccess.com` so re-login is usually a silent redirect chain, but it still needs a top-level navigation (popup), not a fetch.
- **Service tokens** (`service-tokens.mdx`, partial `create-service-token.mdx`, verified): Zero Trust → Access controls → **Service credentials → Service Tokens → Create Service Token** → name → **Service Token Duration** (expiration; API `duration` string such as `"8760h"` = 1 year default; Terraform example `17520h` = 2 years; dashboard also offers *Non-expiring* — **unverified** wording) → Generate → copy **Client Secret once** ("This is the only time Cloudflare Access will display the Client Secret"). Use headers `CF-Access-Client-Id: <CLIENT_ID>` and `CF-Access-Client-Secret: <CLIENT_SECRET>` (a single-header variant via `read_service_tokens_from_header: "Authorization"` exists). Policy must be Action **Service Auth** (Include → Service Token). Renew: "Refresh" extends one year; rotate secrets with a grace period 1 h–30 days. Limit 50 tokens per account. After the first authenticated request Access also issues a `CF_Authorization` cookie for the token session. Optional app setting "401 Response for Service Auth policies" returns 401 instead of a login redirect for unauthenticated requests — turn it on for API hostnames so the app gets a clean status code.
  - From the **browser**, service-token headers are custom headers → they force a preflight and must be in the origin's `Access-Control-Allow-Headers`: **ComfyUI only allows `Content-Type, Authorization`**, so service tokens from the browser work with ComfyUI **only** when Access answers the preflight (option 2 with `CF-Access-Client-Id, CF-Access-Client-Secret` in allowed headers) — but then the actual response still comes from ComfyUI with its own headers, which is fine (allowed-headers is a preflight-only concern). A1111 allows all headers, so either option works. Storing a long-lived secret in the browser's localStorage is a weaker security posture than the OTP cookie; offer it as an "advanced" mode.

### c.3 Summary matrix (browser at www.thewoovee.com → comfy.thewoovee.com behind Access)
| Mode | Preflight handling | Auth carried by | Origin flags needed | Verdict |
|---|---|---|---|---|
| OTP login cookie (recommended) | Access "Bypass options requests to origin" **or** Access CORS settings answering OPTIONS | `credentials:'include'` (same-site cookie) | ComfyUI `--enable-cors-header https://www.thewoovee.com`; A1111 `--cors-allow-origins=https://www.thewoovee.com` | Works; needs a popup login once per session |
| Service token from browser | Access CORS settings answering OPTIONS with `CF-Access-Client-*` in allowed headers | custom headers | same | Works; secret stored client-side |
| Service token via our Worker (`/api/*` on www) | none (same-origin) | Worker adds headers | same (origin still returns CORS headers, harmless) | Works everywhere incl. Safari; media transits the Worker |
| No Access (tunnel only) | origin answers OPTIONS | none | same | Works; the hostname is public — only acceptable with A1111 `--api-auth` Basic auth, and never for ComfyUI (no auth at all) |

## d. Tailscale Funnel as an alternative
Sources: tailscale/tailscale `cmd/tailscale/cli/serve_v2.go` (help text), `ipn/serve.go` (`CheckFunnelAccess`/`NodeCanFunnel`/`CheckFunnelPort`), and tailscale.com/kb/1223 + docs/reference/tailscale-cli/funnel via search snippets (site unreachable in the sandbox — items marked "KB").
- What it is: exposes a local port on the public internet at `https://<machine-name>.<tailnet-name>.ts.net` through Tailscale's relays with a Let's Encrypt cert; the browser sees a normal https origin → no mixed-content or LNA issues. **There is no built-in authentication**: "Tailscale Funnel does not put authentication in front of your service … If the most recent command to configure the port was funnel, then the port will be completely public" (KB). So Funnel is only acceptable for A1111 with `--api-auth` Basic auth, and not for ComfyUI unless the user accepts an open server.
- Enable (KB + source): tailnet admin must allow the `funnel` node attribute in the tailnet policy (`nodeAttrs: [{ target: ["autogroup:member"], attr: ["funnel"] }]`), and HTTPS certificates + MagicDNS must be enabled — the CLI enforces this: `NodeCanFunnel` → "Funnel not available; HTTPS must be enabled. See https://tailscale.com/s/https." and `CheckFunnelPort` → "port %d is not allowed for funnel; allowed ports are: …" (allowed ports come from the `funnel-ports` node capability; the KB lists **443, 8443, 10000** as the only public ports).
- Commands (`serve_v2.go` help, verified): `tailscale funnel 8188` (foreground, Ctrl+C stops), `tailscale funnel --bg 8188` (persistent), `tailscale funnel --https=8443 --bg 7860` (second service on port 8443 → `https://<machine>.<tailnet>.ts.net:8443`), `tailscale funnel status`, `tailscale funnel reset` / `tailscale funnel --bg 8188 off`. Result URL `https://<machine-name>.<tailnet>.ts.net` (port 443 implied). Serve (tailnet-only, not public) is `tailscale serve …` — "To share a local server on the internet, use `tailscale funnel`".
- Limits (KB): bandwidth is capped by non-configurable limits on Funnel relays; only TLS traffic; only ports 443/8443/10000; requires recent client; works on Windows/macOS/Linux (`tailscale funnel` is available in the Windows CLI — KB, **unverified**). Requests arrive at the local service from the local tailscaled proxy (origin `127.0.0.1`), so ComfyUI's default Host/Origin 403 check still applies → `--enable-cors-header https://www.thewoovee.com` is still required, and the `Host` header is the ts.net name.
- Verdict: fine as a zero-config "get an https URL" option for A1111+Basic-auth users who already use Tailscale; not recommended as the primary path because of the missing auth layer. Prefer Cloudflare Tunnel + Access.

## e. Recommended end-user checklist (what the app's "Connect a local server" wizard should say)
**Same PC (fastest)**
1. Use Chrome, Edge or Firefox (Safari cannot reach `http://localhost` from an https site).
2. ComfyUI: start with `--enable-cors-header https://www.thewoovee.com` (portable: edit `run_nvidia_gpu.bat`; Desktop: Manage → launch args; comfy-cli: `comfy launch -- --enable-cors-header https://www.thewoovee.com`). A1111/Forge: `set COMMANDLINE_ARGS=--api --cors-allow-origins=https://www.thewoovee.com` in `webui-user.bat`.
3. In the studio enter `http://127.0.0.1:8188` (ComfyUI; Desktop app `http://127.0.0.1:8000`) or `http://127.0.0.1:7860` (A1111/Forge) and click Test. Chrome will ask "allow local network access" once — click Allow.
**From anywhere (Cloudflare Tunnel + Access)**
1. Have a domain on Cloudflare (free plan is fine). Install `cloudflared` (Windows `.msi`/`.exe`, Linux apt/rpm, macOS brew).
2. Zero Trust → Networking → Tunnels → Create a tunnel → run the shown `cloudflared service install <TOKEN>` command as admin/sudo.
3. Add routes: `comfy.<yourdomain>` → `http://localhost:8188`, `sd.<yourdomain>` → `http://localhost:7860`.
4. Zero Trust → Integrations → Identity providers → add **One-time PIN**.
5. Access controls → Applications → Create → Self-hosted → add both hostnames → policy Allow / Include / Emails = your email → Advanced settings → CORS: **Bypass options requests to origin** ON (or allowed origin `https://www.thewoovee.com`, credentials ON, headers `Content-Type, Authorization`) → Cookie settings: SameSite **None**, HttpOnly on → Create. Optionally enable "Protect with Access" on the tunnel routes.
6. Keep the same CORS start flags on ComfyUI/A1111 as in the same-PC case (the origin must still send `Access-Control-Allow-Origin`).
7. In the studio enter `https://comfy.<yourdomain>` and click Test → a popup opens the Access login → enter email + PIN → close it → Test again. Repeat daily (24 h session) or raise Session Duration.
8. Keep uploads under 100 MB; A1111 jobs must finish in < ~2 minutes (Cloudflare 125 s limit); ComfyUI has no such limit because the studio polls.
**Alternative**: `tailscale funnel --bg 8188` gives `https://<pc>.<tailnet>.ts.net` with no login — only use with A1111 `--api-auth user:pass`, never with a bare ComfyUI.
